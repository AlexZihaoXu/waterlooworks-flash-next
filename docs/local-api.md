# Local listings API

Schema10 adds a separate, read-only `country_inference` contract to workspace postings and posting detail. Existing country source facts/nulls and pay/keyword authority are unchanged. The explicit local country CLI, source-current selection, SVG flag UI, and deployment/pilot safeguards are documented in [inferred work country](country-inference.md). No model calls run on API GET/startup/SSE.

The API requires **server-verified Google login** for every saved-data, FX, refresh/status/log and SSE endpoint. Any Google account may browse once an admin exists; only the owner pinned by `WW_BOOTSTRAP_ADMIN_EMAIL`/`WW_BOOTSTRAP_ADMIN_UID` can become the sole admin of an empty database, and only admin may mutate. Keep one Uvicorn worker. Complete [Firebase configuration, pinned owner bootstrap, schema11 migration and safe transport](firebase-auth.md) before starting it. No containers are required.

## Start explicitly

From the repository root, in Git Bash, after configuring backend-only `FIREBASE_SERVICE_ACCOUNT` and the explicit loopback HTTP development settings documented in [Firebase setup](firebase-auth.md):

```sh
# Read-only server: manual collection is disabled by default.
uv run --project backend --locked uvicorn waterlooworks_flash_next.api:create_app --factory --host 127.0.0.1 --port 8787 --no-access-log --no-proxy-headers

# Enable explicit manual collection instead (headless Chromium; may prompt for Duo).
# First set WW_BROWSER_PROFILE to an absolute private writable directory.
# WW_BROWSER_HEADLESS defaults to 1; explicit 0 permits headed local operation.
WW_ENABLE_REFRESH=1 uv run --project backend --locked uvicorn waterlooworks_flash_next.api:create_app --factory --host 127.0.0.1 --port 8787 --no-access-log --no-proxy-headers
```

Run only one of these commands. Do not enable reload while a collection is active. Chromium must already be installed through Playwright. `WW_DATABASE` optionally selects a database path; `WW_PROJECT_ROOT` selects the repository containing the backend-only `.env` and private browser profile. Defaults assume the repository root working directory.

- **Human documentation:** <http://127.0.0.1:8787/doc> (Swagger UI), **only when the process environment sets `WW_API_DOCS=1`** (for example `WW_API_DOCS=1 uv run ... uvicorn ...`). It is off by default and must stay off in production.
- **Machine schema:** <http://127.0.0.1:8787/doc/openapi.json>, under the same flag.
- **Tracked schema:** [`openapi.json`](openapi.json), generated from the same FastAPI models.
- **Generated frontend types:** `frontend/src/lib/api.generated.ts`.

Swagger UI's Execute button is a real API call. Protected operations require the app cookie; mutations additionally require an allowed Origin, JSON and `X-WW-Request: 1`. Executing the refresh operation starts collection only when enabled; it obeys exactly the same lock/cooldown as the frontend. Swagger UI assets use FastAPI's default third-party CDN and run on the app origin, which is why the docs are opt-in and never proxied by production nginx.

## Routes

| Method | Route                            | Result                                                                                           |
| ------ | -------------------------------- | ------------------------------------------------------------------------------------------------ |
| GET    | `/api/health`                    | Service status and SQLite schema version                                                         |
| GET    | `/api/workspace`                 | Current stored listings and derived summaries; never triggers external fetching                  |
| GET    | `/api/postings/{id}`             | Current saved listing and descriptive content                                                    |
| GET    | `/api/postings/{id}/analysis`    | Current-source facts, reconciled pay, keywords, per-mode extraction status and application route |
| GET    | `/api/postings/{id}/history`     | Actual append-only listing observations with timestamp provenance                                |
| GET    | `/api/postings/{id}/comparisons` | Legacy overlap cohort retained for compatibility; no longer used by Similar jobs                 |
| GET    | `/api/keyword-index`             | Source-current saved fields/keywords for worker scoring; supports ETag/304                       |
| GET    | `/api/refresh`                   | Current progress and bounded sanitized logs                                                      |
| POST   | `/api/refresh`                   | Explicit `{}` JSON body; 202 with run ID if accepted                                             |
| GET    | `/api/refresh/events`            | SSE events named `refresh`; data conforms to `RefreshSnapshot`                                   |

Additional auth routes: `POST /api/auth/prepare` (bounded anonymous cookie), `POST /api/auth/exchange` (verified login/renewal), `GET /api/auth/session` (current UID/role/expiry), and `POST /api/auth/logout` (app-only invalidation). GET `/api/exchange-rates` is also protected. It reads public Bank of Canada reference rates with a single in-flight fetch outside the reader lock: concurrent callers wait for that one result, a success is reused for an hour, and a failed fetch is remembered for 60 seconds so callers receive the fixed 503 immediately instead of queueing behind another timeout. Public health is minimal; documentation/schema contain no saved data. Auth transport and lifecycle details are in [Firebase authentication](firebase-auth.md).

`?once=true` returns one SSE snapshot and closes, for clients testing the stream format. Normal streams send current state on connection and changes thereafter, with keep-alive comments. Reconnection never starts collection. Event payloads are documented in OpenAPI using the `RefreshSnapshot` schema and an `x-event-payload` reference. Each tick rechecks the persisted session and copies refresh state in worker threads, so SQLite opens and the refresh lock never block the event loop. At most 4 concurrent streams per app session (one per open tab) and 32 per server process are admitted; further connections receive a fixed `429` with `Retry-After`, and a slot is released when its stream ends or disconnects.

The workspace payload carries current listings only; per-posting observation history is read on demand from `/api/postings/{id}/history`, so one unreadable revision chain cannot fail the whole workspace. Pay summaries are assembled with a fixed number of set-based queries (no per-posting analysis reads), and the cached response is stored as already-serialized bytes for the member and admin capability variants, so requests do not re-encode it. Workspace and keyword-index responses have bounded, single-entry in-memory caches. Each cache keys on a saved-data generation counter read through a persistent read-only SQLite connection, plus database file identity, not a time-based freshness guess. `open_database` idempotently maintains `data_generation` and `AFTER INSERT/UPDATE/DELETE` triggers on every saved-data table, so writes from the API, CLIs and Node workers all invalidate reuse. Auth/session, credential, OpenAI ledger, run/lease and per-attempt tables (`data_generation.EXCLUDED_TABLES`) are not tracked, so sign-ins, logouts and progress heartbeats keep the cache; cached payload readers must not depend on those tables alone. If any expected trigger is missing (for example after a migration rebuilt a table and before the next open), the key falls back to `PRAGMA data_version`, where any commit invalidates. These triggers are cache plumbing outside the versioned schema; a migration that rebuilds a tracked table may drop them and the next `open_database` recreates them. A write during assembly prevents publishing that result to the cache. Concurrent loads are coalesced, and observers close at shutdown. Large responses use gzip; `text/event-stream` is excluded so progress remains unbuffered. All authenticated responses use `Cache-Control: no-store`; keyword ETag revalidation remains available to the session-scoped worker. Identity and role are never stored in the shared cache; refresh capability is attached per request.

The workspace endpoint is a read-only local snapshot, not a live WaterlooWorks request. It currently returns all stored listings/history for client-side filtering and pagination. Larger histories will require server-side paging later. Country remains null in this listing-only response; stored content is not joined or exposed as a detail view. `details_available=false` describes that UI/API scope, not the absence of content collection.

The keyword-index endpoint is read-only. It selects one latest keyword run/configuration, excludes pending/stale sources and marks partial outputs. Its ETag changes with source hashes, item states or index append generation; `If-None-Match` avoids repeating the full corpus transfer. The browser worker prepares and caches profiles, then ranks the top12 positive weighted-coverage matches outside the UI thread. It does not infer applicant eligibility or replace verified compensation. See [keyword coverage](keyword-coverage.md).

## Saved enrichment authority

`analysis_read.read_analysis` and workspace compensation use the same saved-source enrichment reader. Listing and Similar jobs cards consume workspace `compensation_sort.source_rates`; detail consumes the identical reconciled rates. No GET runs collection, normalization, inference, migrations or writes. Source extraction storage and deterministic/application/history projections are unchanged.

For each mode (salary and keywords), the reader selects the latest run containing that mode, ordered by creation time and run ID—not a posting's last successful extraction. Every selected posting/mode slice must be terminal and match current saved content before any accepted children are exposed. Accepted/partial children must match item posting, content hash, mode, part, rejection count and selected configuration hash, with valid immutable source revision references. The configuration JSON must hash to that identity. Same-configuration cached extractions may originate in an older run. Exact bounded Unicode-code-point evidence spans are checked on read; keyword names must normalize from those spans. Pending, stale, rejected and failed children never become accepted output through fallback to an older source run.

`salary_extraction` and `keyword_extraction` independently report `accepted`, `partial`, `empty`, `rejected`, `failed`, `stale`, `pending` or `not_requested`, with selected run/configuration and slice counts. Empty means accepted extraction with no usable output, not unavailable work or proof that no pay/keywords exist. Partial can include mixed terminal outcomes or withheld invalid evidence. Existing `model_status` describes only the legacy model projection; the new per-mode statuses are the primary UI enrichment status. `keywords` are grounded source mentions, not required/preferred skills or eligibility assertions; validated `skills` remain separate.

New pay is integrated by amount/rate clause rather than broad quote overlap. Compatible legacy/deterministic rates retain grounded hours, eligibility and payout metadata; explicit new currency/period can fill a compatible unknown. Distinct amount spans remain tiers, and repeated same-clause rates collapse. Incompatible interpretations of the same clause are withheld with `compensation_needs_review`; workspace `needs_review` suppresses confident aggregate display/sorting rather than treating a dispute as missing zero. Ambiguous legacy amount anchors fail conservatively into review. When no usable new pay exists, valid source-current legacy/deterministic pay remains available. Unknown display currency and period stay unknown; sorting-only CAD/missing-zero defaults, owner-approved conversion estimates and display preferences are otherwise unchanged.

The reader makes a fixed number of bulk source-index queries per workspace, not an index scan per posting. Detail reads restrict children to its posting. Source grounding is not a completeness or semantic-accuracy guarantee: previously audited omitted periods and stipend remain extraction evidence limitations; this integration does not invent recoveries. Read-only production/browser acceptance requires restarting an older API safely after extraction finishes.

## Refresh safety

1. Explicit JSON POST only; no refresh on startup, GET, SSE connection, page load, or reconnect.
2. A SQLite transaction reserves one running collection before any login starts. Concurrent requests receive **409**, including requests from another server process.
3. Every finished run enforces a persisted **300-second cooldown**. Requests during cooldown receive **429** with `Retry-After`; they do not queue a login.
4. A fresh browser authentication and runtime capture immediately precede collection. Captured page 1 is reused.
5. Listing and detail replays carrying the session cookie share one opener that ignores `*_proxy` environment variables and never follows redirects. Direct listing fetches remain sequential in batches of at most three, with a **2-second completion-to-next-start interval**. Existing transient retry limits remain two retries after **4/8 seconds**; fatal errors stop.
6. Only a completed listing pass is saved. Then the listing-derived detail queue runs sequentially. Each successful plain-text content snapshot is saved atomically with its attempt/revision; later failures preserve completed checkpoints. No application actions, raw HTML, tokens, or cookies are stored.
7. Refresh authentication blocks service workers. The approved refresh lifecycle keeps the browser open with background egress denied through complete `ListingCollection.run()` and the `save_listings()` commit. Inside the first durable detail attempt, context-wide routing then permits at most two distinct observed title-read POST forms on the exact board URL and original frame/ID. Real responses are fetched with zero implicit redirects/retries; metadata is fulfilled to dispatch dependent markup, while validated final markup is cached without rendering and its original request stays pending until browser closure. No responses or opaque actions are invented. Every actual bootstrap request intent is recorded before network access using the shared detail burst budget. After sanitized markup capture the browser closes promptly; first content is reused without refetching, and remaining details use sequential direct HTTP. GET image/font/stylesheet/media/texttrack/script requests are aborted without transport or capture invalidation, even during an active fetch or after capture completion; they never enter templates, the request callback, or the ledger. Script GETs are aborted, never fetched, fulfilled, or executed by this guard. Document/navigation, xhr/fetch, and non-GET requests receive no exemption. Unexpected/duplicate/alternate detail requests, frames, forms, actions, and overlaps remain fatal; an invalid gate stays invalid. Blocked-request diagnostics contain only fixed resource/method/phase/disposition classes and per-class counts saturated at 100,000; inspection/abort failures remain fatal without exposing source values. Failure preserves saved listings/checkpoints and never automatically relogs in. A cap of 12 normally uses 13 actual requests (metadata plus markup plus 11 remaining), or 12 if markup alone suffices, excluding allowed natural retries. Bounded live verification remains required.

Detail attempts (including retries and initial template classification) use bursts of **10**, with **0.6–1.0 seconds** after each burst and an additional **1–2 seconds** every fifth burst. Sleep only occurs before a next attempt; there is no concurrency or final pause. Initial request plus three transient retries wait **5/10/15 seconds** from failure completion. Retry and burst deadlines both apply (their maximum, not a shortened pause). HTTP 408/500/502/503/504 and transient network failures may retry; 429, authentication, redirects, TLS, stale captures and other transport failures stop. A posting whose own detail response fails content validation (schema, size or encoding) is recorded as a failed attempt and the pass continues with the next posting; the run still completes and OpenAI analysis covers the content that was saved. Ten consecutive item failures, or a failure during the first-posting browser bootstrap, stop the pass as a likely broken session. A posting whose latest attempt failed validation is skipped on later refreshes until its listing revision changes. Valid server `Retry-After` is clamped to **24 hours**, persisted on the run for both listing-page and detail 429s, and extends the normal cooldown; nothing resumes automatically.

**Clearing a stale block (operator only).** A mistaken or pre-clamp block is cleared explicitly, offline, with the API stopped (or restarted afterwards: the running API keeps its cooldown in memory):

```sh
cd backend
uv run python -m waterlooworks_flash_next.rate_limit show --database <path-to-sqlite3>
uv run python -m waterlooworks_flash_next.rate_limit clear --database <path-to-sqlite3>
```

This sets `collection_runs.blocked_until` to NULL, prints only timestamps/counts, never contacts WaterlooWorks, and leaves the normal 300-second post-run cooldown intact. Clear a block only after confirming WaterlooWorks is no longer rate limiting you.

`WW_DETAIL_LIMIT=12` is a **server-owned verification cap**, never a client parameter. It limits postings, not HTTP attempts: first-posting metadata classification may add one request; retries add attempts. Normal runs process the full remaining queue. Before details start, refresh skips postings whose saved content comes from the current extractor and whose listing hash is unchanged since their last successful detail capture, plus postings whose latest attempt failed content validation on the same listing revision; the skipped counts are logged and `details_total` covers only the remaining queue. Body edits that leave every listing field unchanged are therefore not re-read. Server-only `WW_DETAIL_FULL_REFETCH=1` (default `0`; any other value fails startup without echoing it) disables both skips for an explicit full detail refetch; it is never a client parameter. Capped totals and `detail_limited` are streamed honestly. Invalid cap values fail startup. Metadata is no longer requested once markup is identified; only `content_only` data is persisted.

The UI keeps the refresh button clickable during an already-running run or cooldown and explains the refusal with a top-centered toast, without sending another POST when the current status already establishes refusal. Offline/in-flight guards remain disabled; the API still enforces 409/429 for races. No cooldown countdown or automatic retry is shown.

`RefreshSnapshot.eta_seconds` is nullable and comes only from the collector's reviewed emitted duration argument. It is the latest estimate, not a client countdown. Unestimated stages, retry waits, saving, and completed states have no ETA. The frontend separately renders an approximate countdown at one displayed second per 1,200 ms, resets to every completed page's latest estimate (including higher or identically rounded estimates), and shows “Updating ETA…” when the estimate expires. The next tick is anchored to the new sample; ordinary renders do not reset it. Detail stages always use API `eta_seconds=null`. Independently, the frontend shows “Fetching posting details” and estimates remaining time from local completed-detail deltas over elapsed time (including rests/retries), sampled every second. It warms up for at least two observed completions and two seconds, resets on run/phase entry, counter regression or total changes, and starts a new baseline after reload without persistence. The estimate is recalculated during stalls rather than counted down; it is approximate, not a completion guarantee. Detail counters are `details_completed`, `details_total`, `detail_requests`, `detail_retries`, `detail_bursts`, and `detail_wait_seconds`, plus `detail_limited`. The frontend changes its progress scale and reloads saved listings once when details begin or the run fails. The progress bar displays a readable stage label (for example “Signing in to WaterlooWorks · Duo approval may be required”, “Collecting listings” or “Extracting with OpenAI”; unknown stages fall back to capitalized words, never raw snake_case) and counts; sanitized log details appear only in a compact expandable console. This console hides three seconds after an observed run ends and stays hidden for historical terminal runs on initial load.

API shutdown requests a cooperative stop: the worker finishes the run as `interrupted` at the next checkpoint (after authentication, between listing pages, between detail postings or between analysis batches), saving a partial listing pass and keeping completed checkpoints. A listing failure likewise saves the pages already fetched (upsert-only, no deletion inferred) before the run fails. A killed process can still leave a durable `running` collection and content attempt. Restore exposes persisted content progress, reports such a row as status `interrupted` with stage `recovery_required` when no live process holds the provider lease, and never replays unfinished attempts. The API deliberately does not finalize it automatically. With the API stopped, run `python -m waterlooworks_flash_next.refresh recover <database>`: it refuses while any live refresh/extraction holds the provider lease, otherwise marks the stale run and its open attempts `interrupted` and prints only counts. Until then, new refresh requests stay blocked with 409. See [deployment recovery](deployment.md#interrupted-refresh-recovery) for the container procedure; never hand-edit SQLite.

The frontend never presents a restored `stage: "recovery_required"` snapshot as a live refresh, even though its persisted status is still `running`: there is no progress bar, ETA or "Refreshing…" state, and the refresh button stays disabled. Instead a warning notice reads "Previous refresh was interrupted" and states that manual recovery is required. A finalized `status: "interrupted"` run shows the same notice, explaining that saved postings may be incomplete and that a new refresh can be started.

## Privacy

Every emitted refresh-stage log is forwarded to the console with its scope, level, reviewed message, and safe arguments, rather than replaced with generic stage summaries. This includes authentication/navigation steps, batch/page counts, ETA, retries, and warnings/errors. DEBUG entries are included when enabled by `WW_LOG_LEVEL=DEBUG`. A reviewed format/text allowlist redacts unknown arguments and withholds unreviewed messages; a regression test requires review of newly added stage log formats. Duo codes, usernames/passwords, request actions, cookies, response bodies, and raw exceptions are excluded. The frontend should display server-supplied errors only through bounded safe messages, never debug dumps. Workspace responses use `Cache-Control: no-store`; the browser must not persist postings, logs, or authentication data in local storage. The frontend persists only the light/dark theme preference (`heroui-theme`). Logs stay in memory, bounded to 200 entries; the console does not pull a reader back to the bottom after they scroll up.

The API rejects unexpected Host headers and requires exact configured origins, JSON and `X-WW-Request: 1` for auth/mutation POSTs. HTTPS/Secure cookies are the default. Explicit loopback-only HTTP development is possible; insecure LAN HTTP is not supported. Do not trust arbitrary forwarded headers. Frontend dev/preview scripts bind to loopback by default. See [transport configuration](firebase-auth.md#transport-and-csrf). Vite denies direct filesystem access to credentials, private experiments, the SQLite data directory, and Pi state, in addition to its standard secret-file exclusions.

### Read-only stored job page

`GET /api/postings/{posting_id}` (`getPosting`) accepts ASCII digit-string IDs without numeric conversion (including leading zeros). It uses a parameterized query on a read-only SQLite connection and returns the current allowlisted listing plus `content` (`content_only` fields) and `content_observed_at`. A known listing without content has both fields null; an unknown ID returns 404. Invalid IDs return sanitized 422 errors. No request starts authentication, refresh, content retrieval, or application actions. No internal attempts or session metadata are exposed.

Title links open `?job=<ID>` within the existing workspace; browse parameters remain intact. Back restores listing focus and scroll, and modifier clicks retain native new-tab behavior. Direct links and reloads read saved content only.

The three analysis reads are also GET-only and use read-only SQLite connections. A deterministic projection is returned only while its listing/content hashes and latest revision identities match current saved source. History contains actual observations rather than interpolated samples and labels legacy/fallback timestamp provenance. Comparisons exclude the selected job and require an exact shared recognized skill, level, or work term. Salary comparison is limited to one known native currency/period pair from the selected job and returns exact fixed/range/open/tier bounds; it performs no midpoint, FX, period, hours, or weeks inference. Missing values remain unavailable rather than zero. Only current-source, current-configuration, evidence-validated model results are displayed; rejected outputs remain unavailable. Validation acceptance is not a claim of comprehensive extraction coverage.

Manual `POST /api/refresh` now runs collection, deterministic normalization, then bounded OpenAI extraction over all saved postings with detail content. It holds the existing durable single-flight claim until analysis terminates. The snapshot exposes `analysis_job_id`, `analysis_total`, `analysis_completed`, `analysis_accepted`, `analysis_rejected`, `analysis_failed`, `analysis_skipped`, and `analysis_cache_hits`. Safe console logs cover normalization, queue/model identity, progress counts, and completion/failure; source bodies and reasoning are never logged. The inference job UUID equals the refresh UUID so restart recovery can restore counts without resuming work. A provider failure preserves collected data and uses the existing `internal` terminal error category with a specific OpenAI-analysis log message. Startup, GET, and SSE reconnect never start collection or inference.

### Targeted disciplines

`GET /api/workspace` includes `targeted_disciplines: string[]` on each posting, projected in one batched read from saved content. Missing values yield `[]`; whitespace, duplicates, and legacy widget marker lines are removed. Full content is not added to the workspace response. The frontend tolerates an older endpoint omitting this field during deployment. Repeated `target` URL parameters retain exact source leaf identities; selection is OR within this filter and AND across filters. No country or theme/degree equivalence is inferred, and no collection or backfill is needed.

## WaterlooWorks admin credentials (schema12)

The admin account/profile button opens Admin settings directly, with bounded WaterlooWorks username/password inputs, Save and Sign out. Members only get Sign out. Backend `require_admin` is authoritative for both `GET` and `POST /api/admin/waterlooworks-credentials`; the existing exact Origin, JSON, `X-WW-Request: 1`, host, HTTPS and session guards remain. Requests are capped at20,000bytes. Username must be a nonblank string of1–256characters; password is a string of1–1024characters preserved exactly. Extra fields and invalid JSON receive fixed input-free errors. Responses are no-store. Save returns only `configured`, `status`, `updated_at`; admin GET additionally returns the explicitly authorized saved `username` (or null). Password, ciphertext and encryption key are never returned. Missing/invalid/wrong key or damaged ciphertext produces a fixed503, never silent recovery.

Schema12 adds `waterlooworks_credentials` (singleton, ciphertext BLOB, updated UTC time) transactionally. Fernet authenticates and encrypts a single JSON pair; replacement verifies the previous token before overwriting it, so tampering/key loss cannot become implicit rotation. Status/readiness authenticates ciphertext without decrypting it. Admin GET may decrypt the existing pair internally for username-only display. Explicit `start_login(database_path, project_root=...)` decrypts one pair before browser/network activity and retains that snapshot for both field entries. The profile now requires explicit private `WW_BROWSER_PROFILE` configuration. Exact ADFS/Duo/WaterlooWorks origins, DEBUG/PWDEBUG refusal and no-trace rules remain. Refresh checks readiness before claiming a run; save never starts login, collection or model analysis. Auth generation, expiry, FIFO/barriers and session/role rules are unchanged.

The modal uses documented HeroUI v3 Modal/Form/TextField/Input/Button composition without appearance overrides. Both fields clear on success/close/logout/account change; only the current bounded15-second operation may update the panel. Closing/aborting a POST does **not** undo a write already accepted by the server. An unconfirmed save asks the admin to reopen/check status before retrying. Autofill is discouraged with browser hints, not a guarantee against password-manager extensions; no draft values are persisted by this app. The saved password has a fixed placeholder mask, no reveal action and no readback; both real fields are required to replace the pair.

### Offline provisioning/deployment

1. Wait for all collection/extraction to finish; stop the backend. Do not mutate a running service's environment. Back up SQLite consistently and restrict the backup's access. Keep the independent key backup separate; key loss is not recoverable by automatic generation.
2. Install the reviewed locked backend dependencies in the stopped service environment (`cd backend; uv sync --locked`). Test `open_database(copy_path).close()` on a backup first: expect schema14, intact integrity/FKs and unchanged source/history/auth rows; review the narrowly scoped inference_jobs CHECK rebuild in [provider migration notes](openai-provider.md). Then perform the reviewed production migration with the same application function. It does not provision keys, authenticate, fetch, or modify previous rows.
3. Only for a migrated database with **no stored WaterlooWorks pair or OpenAI key** and **no existing key**, explicitly run from the repository root:

   ```sh
   uv run --project backend --locked python -m waterlooworks_flash_next.credentials --database data/waterlooworks.sqlite3 --env-file .env
   ```

   This application-runtime command reads the selected environment privately, appends an independently generated key without printing it, and preserves unrelated settings. It never creates/migrates a database, replaces any existing key (even empty/malformed), or generates a key over stored ciphertext. An inherited `WW_CREDENTIALS_KEY`, malformed environment, symlink, hard-linked file, an existing env file that is group/other-accessible or owned by another user, or an initialization lock also refuses provisioning (the file is opened without following symlinks and validated on the open descriptor; permissions are never silently changed, so `chmod 600` an existing file first). A stale `<env-file>.credentials-key.lock` sidecar left by an interrupted run produces a distinct error naming that file: after confirming no other provisioning run is active, delete the sidecar and retry. Stop other `.env` editors first. New files are created mode0600 where supported; explicitly restrict Windows ACLs. Never inspect/print the key with agent tools. If a key already exists, retain it and skip this command; correct mismatches by restoring the matching operator-managed key, not overwriting ciphertext.

4. Restart the backend with its root `.env` read at startup into a private lookup (never exported to the process or browser environment; restart after edits) (or an explicit runtime `WW_CREDENTIALS_KEY`, never a `VITE_` variable). Keep exact configured origins and HTTPS, or the explicit loopback-only development exception. Disable request-body logging, tracing and sensitive diagnostics in reverse proxies/APM/browser tooling. Production artifacts now provide read-only runtime file secrets and private DB/profile volumes; see [encoding, mount permissions and parent deployment gates](deployment.md).
5. The existing app admin signs in and manually enters both WaterlooWorks fields via their account button. Save does not verify WaterlooWorks credentials or start work. Owner-approved real login/refresh and visual acceptance are separate gates. The obsolete root `.credentials.json` is not migrated or read; delete it unread after review while retaining ignore/exclusion protections.

Routine tests use only random secret primitives and empty temporary databases. They do not initialize the real `.env`, read private SQLite, authenticate, claim an actual admin or contact WaterlooWorks.

## OpenAI admin controls (schema13)

Additive schema13 creates only `openai_credentials` and `openai_reauth_challenges` plus indexes. Existing schema12 ciphertext, source/history, auth users and sessions remain unchanged. Reuse the existing `WW_CREDENTIALS_KEY`; **do not run key initialization on an already provisioned deployment**. The offline initialization CLI accepts empty schema12/13/14 and refuses if either credential table contains ciphertext. No key creation or rotation occurs on startup, GET or save. Follow the backup-first, idle/stopped-service recipe above; production migration/restart was not performed by the agent. Tests explicitly migrate only empty temporary databases and random secret primitives.

### Fresh Google verification, not a recent-login shortcut

1. **Reveal** initializes an isolated FirebaseAuth instance with in-memory persistence and calls `POST /api/admin/openai-key/reveal/prepare` with `{}`. The backend validates current admin/session, stores only a hashed random nonce bound to session hash+UID, precise issuance, `not_before=floor(issuance)+1` and a five-minute expiry. Only one challenge/session and1000globally are allowed; issuance cleans expired entries and logout cascades deletion.
2. Preparation asynchronously waits through the second boundary and revalidates challenge/session before responding. The UI then offers **Verify with Google**, a second explicit user gesture that opens the preinitialized popup synchronously. This works with an app cookie after reload even when the main Firebase instance has no current user; it never replaces main auth state or the app session.
3. `POST /api/admin/openai-key/reveal` accepts only challenge and ID token. The existing fixed Firebase project/issuer, google.com provider, expiry and `check_revoked=True` verification applies. The backend additionally requires the same UID and `auth_time >= not_before`, `auth_time <= now`; a preexisting token or forced token refresh does not qualify. Verification has four retained SDK slots and a12-second response bound; timed-out verification never decrypts in the background.
4. In one SQLite write transaction, revalidate the current session/admin, challenge binding/expiry and token freshness; consume once and decrypt the key. The same lock serializes logout and key replacement. A consumed challenge cannot be replayed, including after damaged ciphertext. This flow cannot bootstrap membership, replace a cookie or renew a session. Plaintext appears only in this successful no-store POST response.

All routes require real admin authorization and existing host/transport/exact-Origin safeguards. Mutations additionally require explicit JSON and `X-WW-Request: 1`. Malformed JSON, secret-valued extra keys/fields and all failures have fixed input-free responses. No credentials enter SSE, workspace, status/save responses, logs or persistence in the browser.

## Current refresh authentication status (B2)

`GET /api/admin/refresh-auth` requires the actual current app session and admin role, rechecks both at read time and snapshots only the current running refresh. It returns ephemeral `run_id`, `approval_required`, `code` and bounded `expires_in_seconds`, with `Cache-Control: no-store` on successes and failures. There is no client-selected code/run, persistence, push/resend endpoint or SSE code field. Terminal/expiry clears the memory channel; restart cannot recover a challenge. Nonadmins receive no code and can see only generic approval guidance in refresh events.

Open **Admin settings** from the account button for current Duo approval and recent OpenAI usage/limits. Status polling is visible/open/admin-only, one bounded pair at a time (15-second request bound, five-second delay between pairs). Close/logout/UID change/tab hiding cancel requests and fence late responses. Client expiry subtracts request time, never extending the server deadline. This read-only panel never invokes OpenAI, submits credentials or starts refresh. It does not replace fresh same-admin Google step-up for OpenAI key reveal.

Authentication uses an explicit private `WW_BROWSER_PROFILE`, `WW_BROWSER_HEADLESS=1` by default and sandboxed Chromium, without browser/CDP/VNC exposure. Credential entry and Duo share a fixed180-second deadline; code polling/device trust cannot renew it.
