# Explicit OpenAI inference (schema14)

The Python manual-refresh analysis worker and normal `npm run extract` / `npm run country` engines now use the shared Python Responses client. They do not require a GPU or discover/load local models. This is provider wiring, **not yet production deployment acceptance**: headless/Duo admin status UI is implemented, and [B3 production artifacts](deployment.md) are implemented; actual Docker deployment and real headless SSO/provider validation remain separate gates.

The only provider destination is `https://api.openai.com/v1/responses`, model `gpt-5.6-luna`, reasoning `low`, service tier `default`, `store=false`. Requests use strict JSON schema without temperature or local-model role/thinking delimiters. Original exact source-evidence validators still decide which facts can be saved. Provider refusal, incomplete output, model mismatch and invalid evidence never become confirmed facts. Saving keys, startup and reads never invoke OpenAI. Local benchmark commands remain explicitly local; there is no automatic fallback.

## Limits, accounting and recovery

Configure backend/operator environment `WW_OPENAI_REQUEST_LIMIT` (default20;1–10,000) and `WW_OPENAI_KNOWN_COST_STOP_USD` (default1;0.01–100). Each new explicit run persists these settings; changing environment does not reset an existing run's limits on resume. The second setting is a **known-cost stop threshold, not a hard monetary cap**. Up to four already-dispatched calls can add charges after a threshold is reached. No token-length guess is used to claim a dollar cap. An operator must deliberately raise20 when processing more new/changed work; no full-corpus paid pilot is authorized by these defaults.

Each actual dispatch reserves a durable identity first. Returned usage is finalized before checking output/evidence, including paid rejected/incomplete/error results. Cached/skipped work does not reserve an attempt. The immutable final record is idempotent. Input includes cached read/write subsets; output includes reasoning. Missing or invalid counters/model/tier remain unknown, never zero or assumed Standard. Exact Decimal estimates use the shared dated pricing helper; they are not invoices. See [usage arithmetic](openai-usage.md).

The admin-only no-store `/api/admin/openai-usage` GET reports the most recent20 runs, retained token totals, known/unknown cost totals and persisted limits. The existing Admin settings modal displays these limits, included token subsets and known/unknown costs with visibility-gated bounded polling; members never fetch them. Limits/usage are not proof that analysis completed. Older records remain in SQLite. Raw sources, provider bodies, reasoning, request headers and keys are not ledger data. An incomplete total must not be represented as a complete cost.

A non-2xx response whose body is an OpenAI error envelope without `usage` is a rejected, unbilled request: it is finalized as a known $0 attempt with zero token counters and `pricing_version` marker `error-envelope-http-<status>`, so it neither poisons the run nor blocks resume. A 408/429/500/502/503/504 rejection (except `insufficient_quota`) fails only that posting with `http_client`/`http_server` and the run continues; eight such rejections in a row, or any other rejection status, halt new dispatch. A non-2xx body that is not an error envelope still counts as unknown. If the ledger write after a dispatch keeps failing after two short retries, the attempt stays unfinalized (unknown, never free), the posting is marked `internal` and the job halts and reaches a terminal state.

Transport loss is ambiguous and never automatically retried. Unknown/unpriced attempts (timeouts, transport/body failures, unrecordable outcomes) halt new dispatch and block resume; inspect the safe usage status and provider billing before deliberately starting a new run. An already-dispatched operation is not resent within its run even if its result checkpoint was lost. Budget exhaustion leaves interrupted/stopped/failed work, not a successful full refresh. Existing accepted checkpoints remain saved. There is no force-reanalysis bypass; normal new runs reuse compatible source-current work. Historical jobs with different provider/configuration cannot resume as OpenAI jobs.

Transport bounds:1MiB request body,2MiB uncompressed response body,120-second total deadline,30-second I/O timeout,4,096 output tokens including reasoning, at most four concurrent calls, no redirects, environment proxies or automatic transport retries. Oversized/invalid responses fail safely; usage lost with a transport/body failure remains unknown.

## One private bridge per Node run

Node starts one application-owned Python module over private pipes for the entire CLI run, not one process per slice. It uses the Python executable in `UV_PROJECT_ENVIRONMENT` (or the project's already-provisioned `backend/.venv`), with fixed module arguments and `shell:false`. No install/sync, Fernet implementation, public proxy or key-valued argument is involved. Only Python loads backend environment/secrets and decrypts the encrypted OpenAI key. The bridge never forwards diagnostics to the terminal; model output travels only on its private protocol pipe for evidence validation.

Use the same locked backend environment as the API. Agent validation uses the isolated environment specified in its task, never the running API environment. A direct Python child—not a uv wrapper—allows bounded shutdown to terminate the actual worker and release its OS lock. Framing is newline-delimited JSON, bounded to2MiB incoming lines, four outstanding operations,256KiB final output text,150-second client deadline and24-hour maximum lifetime. EOF drains bounded in-flight work; ambiguity is retained in the ledger. No automatic child restart occurs.

## Cooperative ownership and historical reuse

A nonblocking OS advisory lock at `<canonical database path>.provider.lock` is held from manual-refresh admission **before collection claim** through browser/inference/final cleanup, or for the full standalone inference/CLI bridge lifetime. A busy admission starts no collection, Duo push, provider call or cooldown. Refresh passes explicit ownership into its analysis worker. The stable lock file is never unlinked; process exit releases the lock. All production paths must cooperate. Use one canonical private local database path; hard-link aliases and network filesystems are unsupported. SQLite leases, source-idle and stale-source checks remain additional guards.

Source extraction new-run selection is atomic: compatible current prior items outside a small selection are carried at the same commit, so merely starting/stopping a small run does not hide unrelated accepted results. Non-successful prior slice states are not promoted to success; pending work outside selection is not scheduled. Carried entries point to immutable original extraction rows, never relabel their model. Read-side `origin_run_ids` and `reused_slices` distinguish reuse from new work; run item counts can therefore exceed the selected new-work limit without additional paid requests.

The shared `inference-reuse-contract.json` explicitly pins supported producer/prompt/validator contracts. Original configuration hashes, source revisions/hashes and evidence are verified; tampered/missing/incompatible origins fail closed. Country remains latest-intent per posting, preserving its immutable original run, model, confidence and exact listing/content evidence. Successful unknown country decisions stay unflagged. No arbitrary fallback to older success is introduced after a failed latest intent.

## Offline migration and remaining acceptance gates

Back up SQLite consistently while the application is stopped, including WAL state, and test restoration before deployment. Schema14 adds `openai_runs`/`openai_attempts`. Its narrowly approved exception to additive-only migration rebuilds only `inference_jobs` to extend the exact allowed model/endpoint pair CHECK: the legacy Qwen/loopback pair or fixed OpenAI/Responses pair. It copies/verifies every row, preserves all dependent schema objects, checks FKs/integrity and rolls back on unsupported dependencies. No source history or evidence is rewritten. Key initialization recognizes14 but remains a separate explicit offline operator action; never rotate a key during migration.

Empty-database/primitive tests do not establish real model availability, structured-output acceptance, extraction accuracy, usage-counter availability, live OAuth/Duo behavior or populated-history equivalence. Owner-approved bounded provider evaluation and private-backup migration/read comparisons are mandatory before production use. No paid calls, production migration, remote deployment or live authentication were performed during implementation.
