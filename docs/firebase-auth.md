# Google authentication and shared saved jobs

## Authority and bootstrap

Any successfully server-verified Google account may sign in, but only an **approved** account may read the shared saved dataset: a new account waits as pending until an existing approved user admits it (see [Admission tree](#admission-tree-schema22)). This is an invitation tree, **not** an email/domain allowlist. The first administrator is **pinned by the operator**: on an empty `app_users` table, issuance succeeds only for the identity configured by `WW_BOOTSTRAP_ADMIN_EMAIL` (a Google-verified email, `email_verified=true`, compared case-insensitively) and/or `WW_BOOTSTRAP_ADMIN_UID` (the Firebase UID). When both are set, both must match. That identity becomes the sole administrator and the approved root of the tree; every later Firebase UID becomes a pending member until approved. If neither variable is set, or the verified identity does not match, the first sign-in is refused with the fixed 403 `First administrator must be the configured owner.` and no user or session is created (fail closed). Once an admin exists the pin is ignored, so existing databases are unaffected. A Google popup alone does not claim admin. Client flags, custom admin claims and Firebase project roles do not assign app authority.

Bootstrap and session issuance share one SQLite `BEGIN IMMEDIATE` transaction. `app_users.uid` is unique, a partial unique index permits only one admin, and update/delete guards prevent accidental role changes or reopening bootstrap. Repeat UID logins are idempotent. There is no public promotion, membership editing, deletion or admin-reset API. Owner recovery/transfer requires a separately reviewed offline procedure, not deleting a user through the app.

Set the pin in the backend runtime environment (local ignored `.env`, or Compose's required `WW_BOOTSTRAP_ADMIN_EMAIL` interpolation plus optional `WW_BOOTSTRAP_ADMIN_UID`). These identify the owner and are not secrets, but keep real values out of tracked files; the examples hold placeholders only. Simultaneous first logins are serialized; only the pinned owner can win. Still confirm Admin after the first real Google login before inviting others.

The admin alone may POST refresh; `WW_ENABLE_REFRESH=1` is additionally required. All saved-data reads, FX, refresh status, logs and SSE require an **approved** app session. GET never provisions users, collects, normalizes or invokes a model. The collection service remains single-flight/single-worker; Google membership does not grant WaterlooWorks credentials or an independent collection identity.

3. Owner supplies a private service-account JSON for this same project through **backend-only `FIREBASE_SERVICE_ACCOUNT` or explicit read-only `FIREBASE_SERVICE_ACCOUNT_FILE`**, canonical standard base64 with padding, no whitespace or line wrapping. Base64 is encoding, not encryption. The account needs Firebase Auth user-read permission for the SDK's revoked/disabled-user check (review least privilege, e.g. Firebase Authentication Viewer). Do not supply an OAuth web client JSON or browser API key here.
4. Copy the sanitized `.env.example` yourself to root `.env`, then set the value privately, or inject it through the runtime environment. Existing environment values take precedence. Only backend runtime auth code loads root `.env`; OpenAPI generation/imports do not. `.env` is Git-, Docker- and formatter-excluded. No real `.env` was created or modified by this implementation.
5. Restrict filesystem access and secret-manager access. Never use a `VITE_` prefix, image build ARG, Dockerfile ENV, copied file, browser storage, logs, screenshots or a tracked config for the service account. Production containers receive explicit read-only runtime file secrets, never secret-valued environment or image layers; see [file encoding, ambiguity refusal and mount permissions](deployment.md#runtime-file-secrets-and-permissions). WaterlooWorks credentials now use the separately encrypted schema12 pair and backend-only `WW_CREDENTIALS_KEY`; the legacy `.credentials.json` is obsolete and never loaded. See [offline credential provisioning](local-api.md#waterlooworks-admin-credentials-schema12).

The tracked Firebase modular web config is public and contains no admin key. It initializes Firebase App/Auth only: no Analytics, measurement, Firestore or Storage usage. The Google button uses the existing local `react-icons` multicolored `FcGoogle`, not a remote image or a custom SVG.

Runtime decoding rejects absent/noncanonical/oversized base64, invalid JSON, missing fields, a different project/account/token endpoint and an unusable signing key. No ambient Application Default Credentials fallback is used. An emulator environment is explicitly rejected. Unavailable/malformed configuration fails closed for session preparation, exchange and every protected read/mutation; logout can still invalidate an app cookie. Only fixed errors reach responses; SDK exceptions and token claims are never logged or returned.

## Transport and CSRF

HTTPS and Secure cookies are the default. `WW_AUTH_ORIGINS` is an exact comma-separated list of browser origins (scheme, hostname and port), without paths, wildcards or trailing slashes. Production request Host must exactly match a configured origin authority, including its port. Only the explicit loopback development exception permits the local Vite Host rewrite; the fixed loopback health read grants no auth access. No permissive CORS middleware is installed. Auth prepare/exchange/logout and all mutations require an allowed **Origin**, `Content-Type: application/json`, and **`X-WW-Request: 1`**. Bodies are capped at20,000 bytes before JSON parsing; validation diagnostics are sanitized. Google tokens travel in JSON, never URLs.

For **loopback-only HTTP development**, explicitly set:

```text
WW_AUTH_ALLOW_LOOPBACK_HTTP=1
WW_AUTH_ORIGINS=http://127.0.0.1:5173,http://127.0.0.1:8787
```

Use the same browser hostname consistently. Start the existing Vite and API servers bound to127.0.0.1. The Vite proxy changes Host but retains the browser Origin; validation compares Origin to this explicit list rather than deriving it from the rewritten Host. The HTTP exception also requires a loopback peer. The Vite `main-pc` HTTP host allowance was removed. **Never enable this exception for an HTTP LAN/public deployment.** `http://main-pc:5173` is not an acceptable auth origin and is rejected even with the development exception enabled.

Start Uvicorn with **`--no-proxy-headers --no-access-log`**. Arbitrary forwarded headers must not turn HTTP into trusted HTTPS or rewrite the actual socket peer. Production Compose now uses one explicitly trusted concrete frontend proxy IP (`WW_AUTH_TRUSTED_PROXY`), an exact public Host/Origin and a fixed TLS-only loopback termination boundary. Only that peer's single exact `X-Forwarded-Proto: https` assertion is honored; other forwarding claims are ignored. Secure cookies remain mandatory. See [production TLS boundary and pending owner gates](deployment.md#exact-tls-boundary); do not enable the loopback exception as a workaround. Direct backend HTTPS also remains supported. No actual TLS proxy, remote service or Tailscale Serve configuration was changed.

## Sessions, races and revocation

- The SDK verifies signature, key ID, issuer, project audience, expiry and subject using maintained Firebase Admin verification with `check_revoked=True` and zero clock skew. Issuance additionally requires `firebase.sign_in_provider=google.com` and a bounded nonempty Firebase UID. Email fields do not gate the intentionally any-Google membership policy; a verified email is used only to match the empty-database owner pin. No user/admin/session identity is created before verification succeeds.
- `POST /api/auth/prepare` creates a random256-bit opaque cookie and a five-minute anonymous database reservation, invalidating any previous cookie. Only SHA-256 digests are stored. At most1,000 unexpired anonymous reservations exist: expired rows are removed during preparation and, at the cap, the **oldest reservations are evicted** rather than refusing new sign-ins, so a prepare flood cannot block legitimate users (their reservations are the youngest). At most four exchanges run SDK verification concurrently; missing/expired reservations are rejected before provider verification. True overload (saturated verification slots or SQLite contention past its timeout) returns `503` with `Retry-After: 2` and a fixed message. Production nginx additionally rate-limits `/api/auth/` (5 requests/s, burst20, `429`).
- `POST /api/auth/exchange` handles initial login and renewal. It requires the still-existing reservation/session inside the issuance transaction, and never changes an existing session's UID. Session expiry is `min(verified ID-token exp, now + 3600 seconds, auth_time + SESSION_ABSOLUTE_LIFETIME)`, where `SESSION_ABSOLUTE_LIFETIME` (`app_auth.py`) is **12 hours** measured from the Google sign-in's `auth_time`; refreshed ID tokens keep that original `auth_time`, so renewal cannot extend a session past it and a fresh Google popup is required afterwards. The cookie is HttpOnly, SameSite=Strict, host-only, Path=/api and Secure except for the explicit loopback development exception. Every successful exchange **rotates** the opaque value inside the issuance transaction: the prepared pre-login value is deleted and never becomes authenticated (no session fixation), and on renewal the replaced value keeps only a `ROTATION_GRACE_SECONDS` (30 s) grace for in-flight requests and concurrent tabs. An open SSE stream on the replaced value closes after that grace and the browser's EventSource reconnects with the new cookie. A pending OpenAI reveal challenge is bound to the replaced session and must be prepared again after a renewal. The cookie is opaque, not a signed Firebase token.
- `GET /api/auth/session` returns only UID, app role and expiry; it does not provision anything. Persistent hashed sessions survive API restart until their existing expiry. Anonymous rows cannot access protected routes.
- `POST /api/auth/logout` deletes this app session and clears its cookie. It never invokes project-wide revoke-refresh-tokens, deletes a Firebase user, or changes other apps in the central project. A delayed verification cannot recreate a deleted reservation: logout wins atomically. A late Set-Cookie for the same deleted digest remains unusable. Logout cannot cancel an already accepted collection or bytes already in flight.
- Existing sessions have a **bounded revocation window of at most one hour**, ending no later than their verified Firebase token expiry. They do not query Firebase on every GET. Firebase account disable/revoke is checked again at issuance/renewal. SSE rechecks persisted expiry/logout before each emission, approximately once per second, and closes when invalid. Polling/stream reconnection never renews a session or runs collection.
- Auth and protected responses default to `Cache-Control: no-store`; every `/api/admin/*` response (including the OpenAI key reveal and errors) is forced to `no-store` plus `Pragma: no-cache`. The only handler-set exception is the shared, non-user-specific keyword index, which sends `private, no-cache` with its ETag so the browser must revalidate. No role/UID is stored in the shared workspace snapshot. Per-user refresh availability is attached **after** reading the global cache. The keyword worker can retain its index only in that mounted session's memory and still uses ETag revalidation.

## Browser lifecycle and signed-out shell

The existing responsive header, theme, search, sort, filters, options and layout remain visible while signed out. The results area holds a centered standard HeroUI Card titled **Sign in to continue**, with a neutral secondary **Sign in with Google** button. No skeleton jobs, fabricated filter options, zero-job claims or saved job data are displayed. Search/filter/sort/refresh/pay controls are disabled. Deep-linked posting IDs and a saved foreign-currency preference do not trigger detail, workspace, keyword-index, FX, refresh or SSE reads before the gate opens. Only the bounded app-session check runs on startup.

The protected App subtree mounts after the server returns a valid session. Logout, account change, failed renewal, expiry and errors unmount it, aborting readers and terminating the Similar worker; it is not merely hidden. A successful in-progress renewal (`refreshing`) keeps the same verified UID mounted, so the open job, scroll position and drafts survive the hourly renewal; if renewal, expiry or a session recheck ends the session, the sign-in card shows a “Session ended” warning instead of a silent sign-out. A generation counter prevents stale exchange/renew/session reads from publishing an old identity. Auth writes are ordered, while server logout invalidation is sent immediately even during a pending popup/verification. Cross-tab logout uses BroadcastChannel, and ready sessions recheck on focus and every30seconds. Auth HTTP requests time out after15seconds with generic messages. Renewal has one15-second deadline covering queue wait, Firebase import/token renewal and the complete exchange response. The session expiry watchdog remains armed while refreshing; timeout or logout releases queued work and fences late continuations before further SDK calls, exchange or state publication. Logout invalidation is still sent immediately; its ordered SDK cleanup is also bounded so a stalled import cannot permanently block the next login. Initial sign-in module loading uses the same deadline/cancellation fence independently of the queue, so retrying after a stalled import cannot remain stuck in checking. The user-interactive Google popup stays outside the queue without a popup deadline. Already-started SDK/server work is not claimed to be cancelled.

Manual refresh POST and its follow-up status GET share the current workspace mount's abort signal. Unmount invalidates both requests and fences late success/error/finally updates, including across a new mount. Aborting this client continuation does **not** cancel collection already accepted by the server.

Firebase persists the main sign-in in IndexedDB (falling back to localStorage, then memory) so a reloaded tab, including a phone browser that discards background tabs, can still renew. A signed-in tab renews its ID token before app-session expiry; a reloaded tab uses its surviving app cookie without launching Firebase until renewal is due. A leaked persisted refresh token cannot outlive the server's 12-hour bound from the Google sign-in (`auth_time`). Sign-out and session end clear the persisted user. The key-reveal step-up instance stays in memory. The UI shows checking and sanitized failure states; renewal happens in the background without replacing the workspace. Sign-in failures are split into three fixed, input-free states: a closed or cancelled Google popup (neutral “Sign-in cancelled”), a 401/403 refusal from `POST /api/auth/exchange` (warning “Account not authorized” telling the user to ask the administrator), and everything else, including network, configuration and rate-limit failures (danger “Authentication unavailable”). Server or SDK error text is never displayed. Account switching is sign out followed by the account-selecting Google popup. Real popup behavior, expiry/renewal timing and cross-tab acceptance remain owner-gated browser tests.

## Account menu and optional profile

The header uses an unmodified HeroUI ghost Button, Avatar and Dropdown composition: profile image beside the display name and muted email, with **Sign out** inside the menu. There is no topbar role chip. Missing fields or a failed lookup show **Account** with the generic avatar fallback, never a fabricated name/email. These display fields never establish authority or refresh permissions.

After a ready session UID is available, a separate optional `GET /api/auth/profile` reads Firebase Admin `auth.get_user` using only that verified session's UID. Query parameters are rejected. The strict response includes only nullable `display_name`, `email` and `photo_url`; no tokens, provider records, app role or new stored user fields. This works after reload without persisting Google credentials. Responses are no-store, with no shared profile cache or database migration. Lookup failure does not block the workspace or change the session. The server allows four independent profile lookups and bounds its response wait to12seconds; a timed-out SDK call retains its slot until completion (SDK HTTP timeout10seconds with finite retries). The browser aborts after15seconds and on logout/account change, and fences late results.

Photos are optional HTTPS URLs on the exact Google avatar hosts `lh3.googleusercontent.com` through `lh6.googleusercontent.com`, validated on both sides, rendered with `no-referrer`. Other hosts, credentials, ports and fragments are rejected; the server never fetches photo URLs. Display fields stay in the current tab's memory only. Credential-free checks cover field primitives, empty profiles, real empty-database authorization and click/keyboard sign-out. Real Google profile/photo rendering and visual acceptance remain parent/owner gates.

## Admission tree (schema22)

Schema22 adds `user_approvals`: one row per `app_users` row, created by an `AFTER INSERT` trigger the moment the user row exists, so membership stays immutable and admission state lives beside it. Columns: `status` (`pending`, `approved`, `declined`, `removed`), `parent_uid` (the approver; only for `approved` members), `decided_by`, `requested_at`, `decided_at`, and the sign-in snapshot `display_name`, `email` (Google-verified only) and `photo_url` (the same allowlisted avatar hosts as the profile route). Check constraints keep pending rows decision-free and declined/removed rows parent-free; a `BEFORE UPDATE` trigger keeps the administrator approved and never nested. The migration backfills the existing administrator as `approved` (root) and every existing non-admin member as `pending`: nobody is admitted retroactively, and there is no old tree to import. Firebase remains the identity provider only; admission is app state.

**Sign-in.** On an empty database only the pinned owner may sign in (as admin, approved). Afterwards an unknown identity is inserted as a pending member and gets a session; the token's `name`, `picture` and verified `email` are validated and stored as the snapshot (refreshed on every sign-in/renewal) so approvers can recognise who is waiting. A declined or removed identity is refused at `POST /api/auth/exchange` with the fixed 403 `{"detail": "This account is not approved.", "code": "not_approved"}` and nothing changes. `WW_HOLD_NEW_USERS=1` is the emergency switch: unknown identities get the fixed 403 `{"detail": "This account is waiting for approval.", "code": "account_held"}` and no row at all; existing accounts (pending or approved) are unaffected. The owner-pin refusal carries `"code": "owner_required"`. The browser reads only these allowlisted codes, never the text.

**Enforcement.** `GET /api/auth/session` reports `approval` (`pending` or `approved`) beside `uid`, `role` and `expires_at`. Every session lookup joins `user_approvals` and ignores declined/removed rows, so a withdrawn account's existing cookie answers 401 at once. `require_signed_in` admits any live session and is used only by `/api/auth/session` and `/api/auth/profile` (logout needs no session); every other route goes through `require_session`, which answers the fixed `403 Approval required.` for a pending account, and `require_admin` builds on it. The refresh SSE stream re-checks approval before every emission. Agent API tokens resolve only for approved users (`api_tokens.authenticate` joins the admission row on every request), and Discord alert targets include only approved users' webhooks. A route-enumeration test (`tests/unit/test_approvals_api.py`) walks every registered operation with a pending session and asserts 403 everywhere except health, prepare/exchange, session, profile, logout and the public agent documents.

**Routes** (session cookie, `no-store`, mutations with the usual Origin/JSON/`X-WW-Request` guards and the `{}` body; approve/decline/remove/reinstate are limited to 30 per 10 minutes per user):

- `GET /api/approvals` — approved users: `pending` (id, display_name, email, photo_url, requested_at; oldest first) and `approved_by_me` (id, display_name, photo_url, approved_at; never the email).
- `POST /api/approvals/{uid}/approve` and `/decline` — approved users; the target must be pending (`409` once decided, `404` unknown, `403` for oneself). Decline deletes the target's sessions. Both return the updated listing.
- `GET /api/admin/approvals` — administrator: `root` (the nested tree with `role`, `approved_at`, `approved_by` label and `children`, with emails) and `declined` (declined and removed users, most recent first, with who decided).
- `POST /api/admin/approvals/{uid}/remove` — administrator: an approved member loses access now. Sessions, `api_tokens`, `discord_webhooks` (and their announced bookkeeping) and `posting_marks` are deleted; approvees are re-parented to the removed user's approver (the admin if none); the row stays as `removed` with `decided_by`/`decided_at`. The administrator cannot be removed (`403`).
- `POST /api/admin/approvals/{uid}/reinstate` — administrator: a declined or removed user becomes pending again (`requested_at` reset, decision cleared).

Identifiers are the app UIDs; approvers see pending users' name/email/photo and only the names of people they approved, and only the administrator sees the whole tree with emails. Removal deletes the removed user's personal data (marks, token, webhooks, sessions) rather than keeping it; the admission row and its snapshot remain for the audit list.

**Browser.** A pending session renders the signed-out shell with a **Waiting for approval** card (HeroUI Card/Alert/Button) and **Sign out**; no protected reader mounts and no workspace request is made. The session check polls every 10 seconds while pending (30 seconds otherwise) and on focus; an approval continues the same session, a decline/removal ends it (`Session ended`), and a later sign-in shows **Not approved**. Approved users get **Settings › Approvals**: pending people with **Approve** and a confirmed **Decline…** (AlertDialog portaled into the native settings dialog), **Your approvals**, and the count as a Badge on the account avatar and a Chip on the tab. The administrator also gets **Everyone with access** (nested native lists of HeroUI Avatar/Chip/Button rows) with a confirmed **Remove…** explaining re-parenting, and **Declined and removed** with **Move back to pending**. Refusals show fixed wording derived from the status only; a `404`/`409` reloads the list.

## Schema11 migration and deployment gates

Schema11 adds only `app_users`, `app_sessions`, their indexes and membership immutability triggers. Source/listing/detail/history/normalization/extraction/country tables and their triggers are untouched. No source rows are fabricated or migrated into auth records. CLI extraction reads schema9/10/11/12/13/14; country inference reads10/11/12/13/14; OpenAI writes require14. Older/newer compatibility checks remain strict.

Owner/parent deployment recipe (not performed here):

1. Confirm collection/extraction is idle and no other writer is running. Stop services only through the owner-approved deployment procedure.
2. Make a consistent SQLite backup including WAL state, preserve it privately, and verify restore/integrity on an offline copy.
3. On the **backup copy first**, call `open_database(copy_path).close()` with the new backend, inspect `PRAGMA user_version=14`, integrity/FK checks and all source/history table counts. No normalization, inference or collection is part of migration.
4. Only after review, migrate the production database using the same explicit primitive or the next approved API startup (startup migrates but never creates an admin). Do not start old schema10 tools against the upgraded database.
5. Configure the private backend service account, explicit origins and safe TLS. Start a single worker with proxy/access logging safeguards. Set `WW_BOOTSTRAP_ADMIN_EMAIL` (and optionally `WW_BOOTSTRAP_ADMIN_UID`) to the owner's identity. Owner completes Google sign-in first and verifies Admin; then verify a second real Google account is Member and receives403 on refresh.
6. Verify browser logout/account-switch clearing, expiry/renewal, existing SSE closure, restart session persistence, forged/non-Google/revoked token rejection and HTTPS/cookie behavior. Keep the instance closed until these live gates pass. No live sign-in/admin claim, production migration, refresh, collection, model invocation or deployment was performed by the implementation agent.

Tracked tests use empty SQLite and UID/session/ASGI primitives. Test-only FastAPI overrides bypass **only Firebase configuration readiness**; real session hashing/lookup/expiry, role checks, CSRF and transport enforcement still execute. Tests do not mock the verifier/provider or fabricate postings/provider responses. Missing/malformed config tests have no override. SDK signature/revocation verification and populated production migration are explicitly not claimed as live-verified.

## Admin settings step-up exception

The saved WaterlooWorks username/email is explicitly authorized for admin-only display; its password is never returned or revealable. Schema13 additionally stores an encrypted OpenAI key and short-lived hashed reveal challenges. OpenAI plaintext is returned only by the dedicated no-store reveal POST after another Google OAuth verification for the same admin UID/current app-session hash, with `auth_time` strictly after challenge issuance across second-resolution boundaries. No recent-login, `iat`, token-refresh or checkbox shortcut is accepted. The isolated in-memory Firebase popup instance supports reloads without changing main auth FIFO/generation/renewal behavior or replacing the app cookie. See [protocol, migration and owner acceptance](local-api.md#openai-admin-controls-schema13). These are narrowly scoped runtime authorizations, never permission for agents, logs or browser storage to expose secrets.
